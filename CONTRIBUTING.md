# Contributing to Redivivus

Redivivus is Diablo II: Lord of Destruction 1.14d turned back into C++ that builds and runs.
Most of the tree is **generated** from reverse-engineered Ghidra databases, which changes where a
contribution has to land. This file is about that: not etiquette, but which door a given finding
goes through so that it survives.

If you are unsure, [ask on Discord](https://discord.gg/MHK2Dg9) or just open an issue. A finding
filed in the wrong place is still a finding; it only costs a redirect.

## What is generated and what is not

Every generated file starts with the line:

```
// Auto-generated by ghidra-mcp - DO NOT EDIT
```

| | |
|-|-|
| **Generated** - edits are overwritten | the module directories (`D2Client`, `D2Common`, `D2Game`, `D2Win`, `D2gfx`, `Storm`, `Fog`, `Bnclient`, `D2CMP`, `D2DDraw`, `D2Direct3D`, `D2Gdi`, `D2Glide`, `D2Lang`, `D2Launch`, `D2MCPClient`, `D2Multi`, `D2Net`, `D2Sound`), `globals/`, `d2_enums.h`, `d2_platform.h` |
| **Hand-written** - pull requests welcome | `cmake/`, `docs/`, `support/`, `thirdparty/`, `asm_matching/`, `tools/`, `agent/`, `CMakeLists.txt`, `.github/`, `README.md` |

An edit to a generated file compiles and then disappears at the next regeneration. The finding
behind it is usually the valuable part, so the point is to land it somewhere upstream of the
generator rather than in its output.

## Which door

### A wrong name, type, field, prototype or calling convention

This is the common case, and it belongs in Ghidra. Two ways in:

- **As a proposal**, if you have agent access to the databases (below). It is checked against the
  database, reviewed, and applied with you as the git author.
- **As an issue**, using the *Correction: name, type or prototype* template.

Either way it is one claim per report, addressed **by address** - names change, addresses do not  - 
with the value you saw and evidence a reviewer can re-check. The house rules on naming, prefixes
and what counts as evidence are in
[`agent/skills/redivivus/SKILL.md`](agent/skills/redivivus/SKILL.md); read it before proposing,
whether or not you use an agent. The short version of its evidence ranking, strongest first: the
developers' own words (assert strings, `__FILE__` paths), the paired function on the Mac build,
field accesses on an already-typed struct and the names of the callees it feeds, strings it
references, and only then inference from behaviour.

### A function Ghidra has not found, or wrong function boundaries

Data that is really code, code that is really data, a function that should split or merge. Use the
*Structural: function discovery/boundary* template. This is **never** a proposal and never a pull
request.

The reason is cost. A change to the function set moves the set of translation units, so it
invalidates every cached artefact - the dependency graph, the per-function export, the emitted
tree. It cannot be absorbed incrementally; it forces a full rebuild. So a human applies it in the
writable database and schedules that rebuild.

### The generated C++ is wrong in a way no Ghidra change fixes

A lost value, a bad transform, a frame artefact - the decompiler read it correctly but the
generator emitted it wrongly. That is a generator bug. Open an issue here with the function
address and the emitted code; the fix lands in
[ghidra-reconstruct](https://github.com/jaenster/ghidra-reconstruct) and becomes a regression
fixture, so the same bug cannot come back.

A handful of functions have no faithful C spelling at all and carry hand-supplied bodies instead;
[`ghidra-reconstruct/overrides/README.md`](https://github.com/jaenster/ghidra-reconstruct/tree/main/overrides)
documents each one and why.

### A crash while playing

Open an issue and attach the `d2crash-<date>-<time>.txt` report written next to the executable. It
carries a symbolised stack trace. Every crash so far has been a single wrong type or a lost value
in the reconstruction, and each one fixed takes a class of others with it - so these are valuable
reports, not noise. Do not patch around a crash in generated source.

### Build, docs, tooling, matching

Ordinary pull request. See [docs/building.md](docs/building.md) for the toolchain, and
[`asm_matching/`](asm_matching/README.md) for the byte-match harness. If a change moves the match
figures, say what it does to them.

### A deliberate deviation from the original

Sometimes the source *should* differ from 1.14d - a string that must read "Redivivus" rather than
"Diablo", for instance. These are accepted as pull requests, but they have to be re-applied after
every regeneration, so they end up captured as rewrite operations rather than kept as a source
diff. Say plainly in the PR that this is what you are doing.

## Reading the databases yourself

The Ghidra databases behind the tree - 1.14d Windows and the Intel Mac build from the same source
revision - are open to read for anyone with an AI agent, through a read-only MCP server. In Claude
Code:

```sh
claude plugin marketplace add jaenster/redivivus
claude plugin install redivivus@redivivus
```

Then sign in with GitHub from `/mcp`. The plugin brings the server and the house rules. Other
agents: <https://redivivus.app/agent-setup/prompt.md>. How proposals work:
<https://redivivus.app/about#contributing>.

Everything exposed is read-only. Address functions and data by address, start narrow (one function,
then its xrefs and callees) rather than fanning out, and do not define or disassemble anything to
"check" a suspicion - report it from the xrefs, the surrounding bytes and the table you found it
through.

## Scope

Redivivus is a **single-player** project, made to study and preserve the game. Online play on
Battle.net is outside its scope: it is not designed, tested or supported for it, and changes aimed
at it are out of scope.

This repository holds **no game data**. You need your own Diablo II: Lord of Destruction 1.14
installation to build and run it, and no contribution may add game assets, extracted data files or
copyrighted content from the original.
