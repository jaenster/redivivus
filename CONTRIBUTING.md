# Contributing to Redivivus

Redivivus is Diablo II: Lord of Destruction 1.14d turned back into C++ that builds and runs.
The tree was **generated** from reverse-engineered Ghidra databases, and a growing part of it is now
hand-written function by function against the original binary. That changes where a contribution
has to land. This file is about that: not etiquette, but which door a given finding goes through so
that it survives.

If you are unsure, [ask on Discord](https://discord.gg/MHK2Dg9) or just open an issue. A finding
filed in the wrong place is still a finding; it only costs a redirect.

## What is generated and what is not

Files that came out of the generator start with the line:

```
// Auto-generated by ghidra-mcp - DO NOT EDIT
```

The line is historical. The tree is no longer regenerated wholesale: every function body that has
been rewritten by hand is pinned in the maintainers' ratchet store, so it survives any later regeneration, and the
generator is not run over the published tree at all. What that means for a pull request:

| | |
|-|-|
| **Function bodies** - pull requests welcome, under the rules below | everything under `Source/` (the module directories `Source/D2Client/`, `Source/D2Common/`, `Source/D2Game/`, `Source/Fog/`, `Source/Storm/`, ...), and `3rdparty/crashy/` |
| **Declarations** - through Ghidra, not a pull request | names, types, struct fields, prototypes and calling conventions, wherever they are spelled: the shared headers in `Source/D2Headers/`, the global data in `Source/globals/`, the unit headers |
| **Hand-written** - pull requests welcome | `project.json` (the module table), `Redivivus/`, `3rdparty/libbacktrace/`, `3rdparty/implibs/`, `cmake/`, `docs/`, `asm_matching/`, `tools/`, `agent/`, `CMakeLists.txt`, `.github/`, `README.md` |

## Which door

### A function body that does not match the original

Pull requests that change a function body under `Source/` are welcome when the body compiles to the
original. The bar:

- `oracle diff <name>` shows **MATCH** for the function (or a clear improvement: say which), and no
  other function in the same translation unit loses MATCH. The harness is in
  [`asm_matching/`](asm_matching/README.md).
- **One function per commit**, its address in the message.
- **Faithful source only.** No `noinline`/`forceinline`, `volatile`, inline `asm`, `#pragma` or
  `register` to force the compiler's hand; no raw addresses; no dead stores; no temporaries that
  exist only to steer register allocation or instruction placement. A temporary that captures a
  value in the order the asm evaluates it is fine, with a `// steer-ok: <reason>` comment on its
  line saying what the asm shows.
- House getters and the existing `FlagBit_` getters are fine where the original inlined the same
  check; an `inline` on a same-unit callee the original inlined is fine too.

A maintainer re-verifies every body against the binary and pins it in the ratchet store before it lands,
so it survives anything that later touches its unit. If the body only matches with a different
name, type or prototype, that part is a declaration: send it through the door below and say so in
the pull request.

### Sizes and offsets

The original passed `sizeof(T)` to its allocators, `memset` and `memcpy`, indexed arrays and named
fields. The decompiler folds all of that into numbers; a body here spells it back:

- a size is `sizeof(T)`, `sizeof(x)`, `sizeof(T) * n` or `offsetof(T, field)` for a deliberate
  partial clear, never a folded literal like `memset(p, 0, 0x3c)`;
- a member is the real field (`p->pNext`), never `*(int*)((char*)p + 0x24)`: if the field is
  missing or wrong, that is a declaration (the door below);
- a stride is array indexing or `sizeof`, never `p += 0x18`; a loop bound over an array is
  `_countof(a)` (`sizeof(a) / sizeof(a[0])` for a member of a packed struct, which mingw's
  `_countof` cannot bind);
- `char sz[MAX_PATH] = "";` rather than the `sz[0] = 0; memset(sz + 1, 0, 0x103)` it compiles to.

Next to a type whose size a change relies on, once per type, prove the 32-bit value is unchanged:

```cpp
static_assert(sizeof(void*) != 4 || sizeof(D2GfxInfoStrc) == 0x3c, "D2GfxInfoStrc is 0x3c bytes on x86");
```

A byte offset into a raw buffer (packet bytes, a file image) really is one and stays. CI runs
`node asm_matching/lint/literal-sizes.mjs --baseline asm_matching/lint/literal-sizes.baseline.tsv`;
no file may go above its count in the baseline.

### A wrong name, type, field, prototype or calling convention

This is the common case, and it belongs in Ghidra: a declaration is shared by every function that
uses it, so it is applied in the database and in the tree together. Two ways in:

- **As a proposal**, if you have agent access to the databases (below). It is checked against the
  database, reviewed, and applied with you as the git author.
- **As an issue**, using the *Correction: name, type or prototype* template.

Either way it is one claim per report, addressed **by address** - names change, addresses do not  - 
with the value you saw and evidence a reviewer can re-check. The house rules on naming, prefixes
and what counts as evidence are in
[`agent/skills/redivivus/SKILL.md`](agent/skills/redivivus/SKILL.md); read it before proposing,
whether or not you use an agent. The short version of its evidence ranking, strongest first: the
developers' own words (assert strings, `__FILE__` paths), the paired function on the Mac build,
field accesses on an already-typed struct and the names of the callees it feeds, strings it
references, and only then inference from behaviour.

### A function Ghidra has not found, or wrong function boundaries

Data that is really code, code that is really data, a function that should split or merge. Use the
*Structural: function discovery/boundary* template. This is **never** a proposal and never a pull
request.

The reason is cost. A change to the function set moves the set of translation units, so it
invalidates every cached artefact - the dependency graph, the per-function export, the emitted
tree. It cannot be absorbed incrementally; it forces a full rebuild. So a human applies it in the
writable database and schedules that rebuild.

### The C++ is wrong in a way no Ghidra change fixes

A lost value, a bad transform, a frame artefact - the decompiler read it correctly but the
generator emitted it wrongly. Open an issue here with the function address and the code; for a
single function the fix is usually a hand-written body (above), and a pattern across many functions
goes to [ghidra-reconstruct](https://github.com/jaenster/ghidra-reconstruct) as a regression
fixture, so the same bug cannot come back.

A handful of functions have no faithful C spelling at all and carry hand-supplied bodies instead;
[`ghidra-reconstruct/overrides/README.md`](https://github.com/jaenster/ghidra-reconstruct/tree/main/overrides)
documents each one and why.

### A crash while playing

Open an issue and attach the `d2crash-<date>-<time>.txt` report written next to the executable. It
carries a symbolised stack trace. Every crash so far has been a single wrong type or a lost value
in the reconstruction, and each one fixed takes a class of others with it - so these are valuable
reports, not noise. Do not patch around a crash; fix the wrong type or the lost value it comes from.

### Build, docs, tooling, matching

Ordinary pull request. See [docs/building.md](docs/building.md) for the toolchain, and
[`asm_matching/`](asm_matching/README.md) for the byte-match harness. If a change moves the match
figures, say what it does to them.

### A deliberate deviation from the original

Sometimes the source *should* differ from 1.14d - a string that must read "Redivivus" rather than
"Diablo", for instance. These are accepted as pull requests and pinned like any hand-written body,
but they are kept apart from the byte-match figures. Say plainly in the PR that this is what you
are doing.

### Work items

Curated tasks are on <https://redivivus.app/work>: functions a few instructions off a byte match,
file-statics whose register convention holds their callers back, and declaration facts, each with
a diagnosis and a suggested approach. With the Redivivus MCP server your agent reads them with
`list_work` and `get_work` (the brief, including the `oracle build`, `check` and `diff` lines to run).

1. Claim the item first (`claim_work`), so nobody duplicates the work. A claim is a 48-hour lease,
   renewable up to 7 days. Translation units marked "maintainers (lane ...)" on /work are being
   worked through by the maintainers and cannot be claimed until the lane ends.
2. Work it the way any function body is worked (see "A function body that does not match the
   original" above): faithful source only, `oracle check` on the unit shows no lost MATCH.
3. Open the pull request with one line per item in its description:

   ```
   Work-Item: <id>
   ```

   `pr_template {ids: [...]}` writes the whole description, with each function's status before and
   after and the callers it unlocks that now match. The line links the pull request to the item and
   hands it in for you as the PR's author; you can still call `submit_work` with the PR link and a
   note. A Work-Item line naming an item someone else holds is flagged on /work, not linked.
4. Once the merged change shows every function of the item MATCH in the published measurement, the
   item closes on its own and counts for you. A pull request closed without merging puts the item
   back in the pool after three days, unless you hand it in again with another one.

Declaration facts (a prototype or type the original evidently had) land in Ghidra through
`propose`, not in a pull request; put the proposal id in `submit_work`'s note.

## Reading the databases yourself

The Ghidra databases behind the tree - 1.14d Windows and the Intel Mac build from the same source
revision - are open to read for anyone with an AI agent, through a read-only MCP server. In Claude
Code:

```sh
claude plugin marketplace add jaenster/redivivus
claude plugin install redivivus@redivivus
```

Then sign in with GitHub from `/mcp`. The plugin brings the server and the house rules. Other
agents: <https://redivivus.app/agent-setup/prompt.md>. How proposals work:
<https://redivivus.app/about#contributing>.

Everything exposed is read-only. Address functions and data by address, start narrow (one function,
then its xrefs and callees) rather than fanning out, and do not define or disassemble anything to
"check" a suspicion - report it from the xrefs, the surrounding bytes and the table you found it
through.

## Scope

Redivivus is a **single-player** project, made to study and preserve the game. Online play on
Battle.net is outside its scope: it is not designed, tested or supported for it, and changes aimed
at it are out of scope.

This repository holds **no game data**. You need your own Diablo II: Lord of Destruction 1.14
installation to build and run it, and no contribution may add game assets, extracted data files or
copyrighted content from the original.
